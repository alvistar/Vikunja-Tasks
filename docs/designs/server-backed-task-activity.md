## Problem Statement

Veyrn has no task comments: no model, API wrapper, UI, or offline operations. A returning solo user cannot reconstruct a long-running task from a coherent history. Stable context is currently mixed with dated updates in the task description, while subtasks describe what remains to be done.

The feature must make a task tell one truthful story without requiring a user to remember to document every state change manually.

## What Makes This Cool

The detail sheet becomes a calm, chronological account of a task:

```text
2 September
✓ Spedire Mac mini a InPost Svapoweb completed · 15:19
Alessandro · Pacco consegnato al punto Svapoweb. · 15:20

1 September
◷ Task created · 10:03
```

A manual comment adds human context. Server facts add the events the user should not need to transcribe. There is one chronological story, not a comment area beside a separate activity log.

## Decisions

- **Target user:** returning solo Veyrn user. The task detail must make a task resumable after days or weeks away.
- **Timeline sources:** only API-backed, semantically identifiable facts: task creation, task or subtask completion, and Vikunja comments. A generic `updated` timestamp is excluded because it does not identify the changed field.
- **Comments:** the API-contract spike is a release gate. It records the live v2 read/create/update/delete endpoints, methods, pagination and permission fields before UI work starts. The client exposes only operations confirmed by that probe; if an operation is unavailable, its control and acceptance criterion are removed through a design revision rather than guessed.
- **Offline:** comment mutations appear immediately and use Veyrn's durable outbox. They survive restart and retry during sync.
- **No invented local audit trail:** no device-only events and no automatic synthetic comments. The UI never implies an exhaustive record of actions made by other clients.
- **Future direction:** a personal cross-task activity stream reuses the same projected activity items. It is not in this release.
- **No data migration:** existing descriptions remain unchanged. New comments are used for new activity.

## Constraints

- Veyrn's current `VikunjaTask` model decodes `done` and `updated`, but drops server fields such as `created` and `done_at` (`VikunjaCore/VikunjaModels.swift:5-28`).
- A live API response for task `#10` exposes `created`, `done_at`, and related subtasks with their own `done_at` values. It is enough to make completion events server-backed.
- `InlineTaskEditor` has a 440–520 pt macOS width and an existing task-detail hierarchy: title, description, chips, subtasks, footer (`VikunjaWidgetApp/InlineTaskEditor.swift:117-135`).
- Veyrn's `Outbox` currently queues task create/update/complete/reopen/relation operations only (`VikunjaCore/Outbox.swift:19-25`).
- The server comment API must be treated as the source of truth. The client must not append an activity journal to the task description.

## Interaction Design

### Information hierarchy

The task title and current task controls remain first. The subtask card remains above Activity because it answers “what remains?”; Activity answers “what happened?” and appears immediately below it.

Activity is **collapsed to a visible preview** on first open: header `Activity`, latest event’s icon/source/text/timestamp, and a textual `Show N activity items` control. The preview is not an empty closed accordion. Selecting the control expands the full chronological feed in place and changes its accessible label to `Hide activity`; it does not navigate away, reset the task editor, or discard a composer draft. The remembered expanded/collapsed preference is per task-detail session only.

The compact single-line composer is **always visible below the preview**, with the label `Add an update` remaining visible after text entry. It submits from its trailing send control, preserves typed text on any failed attempt, and expands Activity after a successful submission so the new item is immediately visible in context. The composer never opens a separate sheet.

### Time and event language

Activity groups events with localized calendar headings: `Today`, `Yesterday`, otherwise the locale’s full calendar date. Each row shows only the localized time. It never uses relative elapsed strings such as “18 min ago”, because the task diary must remain precise when read later. Automatic rows name a concrete server fact (`Task created`, `Completed <subtask title>`); comment rows lead with their author and text. Icons distinguish event kind but never carry meaning without the adjacent text.

### Visible interaction states

| State | What the user sees | Primary action |
|---|---|---|
| Loading | `Activity` header with a short inline progress label; no empty-state copy until the first fetch resolves | None |
| Empty | `No activity yet` plus `Add an update` at the composer; explains that completed subtasks and comments will appear here | Add update |
| Loaded/collapsed | Latest event preview and `Show N activity items` | Expand |
| Loaded/expanded | Chronological event rows; `Load earlier activity` only when another server page exists | Load earlier / add update |
| Pending | Comment row uses a subdued `Sending when online` status; it remains readable and editable by its author | Edit / cancel |
| Retryable failure | **Activity-wide banner**: `Some updates are waiting to send` with a Retry action; affected rows retain a subdued pending indicator | Retry |
| Permanent failure | **Activity-wide banner**: `An update needs attention` with `Review updates`; the banner opens the existing Pending Changes recovery surface rather than adding inline destructive controls | Review updates |
| Fetch failure | Existing rows stay visible; an Activity-wide `Couldn’t load newer activity` banner includes Retry | Retry |

### Responsive and accessibility requirements

- **macOS:** keyboard order is Activity disclosure, composer text field, Send, then activity-row actions. `Return` submits only when the composer has text; `Escape` clears neither the draft nor the expanded state. The disclosure remains a native button with an explicit `Show N activity items` / `Hide activity` accessibility label.
- **iOS:** disclosure, Retry, `Review updates`, Send, edit, and delete controls have a minimum 44 by 44 pt hit target. The composer grows vertically up to three lines before internal scrolling; keyboard appearance keeps Send visible.
- **Dynamic Type and narrow widths:** preview event text can wrap to two lines; timestamps move beneath text rather than truncate; long subtask titles wrap before activity rows. No text relies on a fixed row height.
- **VoiceOver:** each event is one logical element announced as `<event kind>, <calendar date>, <time>, <content>`; icons are decorative when that text is present. The activity-wide failure banner announces once when it appears and its action names the outcome (`Retry updates`, `Review updates`).
- **Contrast and state:** pending/failed status never depends on color alone; it includes text and a symbol. Body copy follows the existing primary/muted token contrast rather than adding new low-contrast greys.

### Comment actions

Only a comment for which the API grants edit/delete permission shows a trailing ellipsis with a 44 pt hit target and accessibility label `More actions for your update`. It opens a native menu: `Edit update`, separator, `Delete update` in destructive styling. Automatic events and comments without permission show no empty or disabled action control. On iOS, a trailing swipe exposes the same Edit/Delete actions as a fast shortcut; the ellipsis remains the discoverable and cross-platform fallback. Delete uses the app’s native destructive confirmation before queuing the operation.

## Activity and Comment State Model

### Event boundary and ordering

The projection receives exactly one server task, its **direct** `related_tasks.subtask` children returned by the task-detail endpoint, and the paginated comment collection for that task. It does not recurse into grandchildren and does not turn `updated` into an event.

Each projected item has a stable identity and is ordered by the deterministic tuple `(timestamp descending, kind precedence, stableID ascending)`. For equal timestamps, automatic events precede comments; automatic kinds order `created`, `completedTask`, then `completedSubtask`; server IDs are stable IDs for server entries. This makes the projection predictable and unit-testable.

### Pagination contract

The API-contract spike records the API's sort direction, page-number and total-page shape. `CommentPage` requests the newest supported page when detail opens, then merges that page with all automatic events, which are never paginated away. If a previous page exists, the activity footer shows `Load earlier activity`; activating it appends that page by number, suppresses comments whose server ID already exists, and preserves the current scroll anchor. A partial page means automatic events plus the loaded comment range are visible and the footer remains available. An empty page with no automatic events shows the explicit empty state.

### Comment identities and offline transitions

A locally created comment has a client UUID until the create acknowledgement returns its server ID. The outbox maps that UUID to the server ID and replaces the optimistic item in place, so a list never duplicates the same comment.

Create is required for this feature. The edit and delete rows below are conditional capabilities: they are implemented only if the API-contract spike confirms their endpoint, method, permission fields, and error semantics.

| Offline sequence | Outbox behavior | Server result |
|---|---|---|
| Create | Queue `commentCreate(clientUUID, text)` | One created comment after sync |
| Create → edit | Coalesce into the queued create with final text | One created comment with final text |
| Create → delete | Cancel the queued create and remove the optimistic item | No server comment |
| Server comment → edit, if confirmed | Queue `commentUpdate(serverID, text)` after its create dependency is resolved | One edited comment after sync |
| Server comment → delete, if confirmed | Remove queued updates, queue `commentDelete(serverID)` | Comment removed after sync |

The comment-outbox schema spike is a second release gate. It proves that a separate, account-scoped and versioned `CommentOutbox` can encode `clientUUID`, `serverID?`, `TaskRef`, text, operation kind, dependency ID, retry state, and any server-supported idempotency/correlation key while leaving the existing `PendingOp` payload untouched. It defines an atomic persisted replacement of `clientUUID` with `serverID`, replay behavior after an ambiguous network outcome, and a migration path for future comment-outbox schema versions.

The comment queue has explicit states: `pending`, `retryableFailed`, `permanentlyFailed`, `acknowledged`, and `cancelled`; an unsaved composer draft is outside the queue. A detail refresh is blocked by `pending` and `retryableFailed` comment operations for that task, but permitted with a `permanentlyFailed` operation so the server timeline stays fresh while the failed item remains visible with recovery actions. `acknowledged` and `cancelled` entries are removed from the queue. When a refresh is permitted, server comments merge by server ID and local optimistic items/drafts remain until their own terminal transition; a global outbox drain never overwrites local state.

### UI states and authorization

The activity section has explicit loading, empty, loaded, partial-page, pending, and failed-fetch states. A pending mutation shows its unsynced state; a failed mutation exposes retry without discarding the item or draft. Edit and delete controls render only when the API response's confirmed ownership/permission field permits that operation. The contract spike records the precise field and rule; the UI must not infer permission solely from a display name.

## Premises

1. A timeline built from `created`, `done_at`, and comments is useful even though it cannot report a due-date, title, priority, or reopen change made by another client.
2. Completion events are valid automatic entries because the server supplies both an unambiguous event meaning and a server timestamp.
3. Generic `updated` rows are noise: the timestamp has no field-level explanation and must not be rendered as progress.
4. Comments and automatic entries can share a chronological projection while retaining visibly different source labels and iconography.

## Approaches Considered

### A. Timeline in the editor

Compute and render activity directly inside `InlineTaskEditor` after adding comment API support and timestamps. Fastest initial surface, but projection and ordering become coupled to SwiftUI. Rejected because the future personal activity stream would duplicate this logic.

### B. Activity domain layer

Add a pure `TaskActivityItem` projection that merges comments, task creation, and task/subtask completion. `TaskStore` coordinates fetching and comment outbox operations; `InlineTaskEditor` renders the result. Chosen because the same tested projection can feed both the current detail view and a later personal activity stream.

### C. Audit trail upstream in Vikunja

Add field-level activity history to the Vikunja server and consume it from Veyrn. This would give complete cross-client history, but it is a separate upstream project and delays client comment support. Deferred as a separate initiative.

## Recommended Approach

Build the activity domain layer.

1. Run two formal release-gate spikes first. The API-contract spike records endpoint paths, HTTP methods, request/response samples, pagination, ownership/permission fields, error shapes, and whether task detail always includes direct subtasks with `done_at`. The outbox-schema spike proves persisted comment operations, UUID-to-server-ID replacement, idempotent replay, and backwards-compatible decoding of existing queued task operations. Create isolated test accounts/projects/tasks and an explicit cleanup owner for integration tests. Do not start UI work until both artifacts close the blocking questions.
2. Extend API models to preserve server timestamps required for activity: `created` and `done_at`; add `VikunjaComment` with the fields proven by the contract spike.
3. Add routed v2 API wrappers only for comment operations confirmed by the spike, including pagination and typed permission/validation failures.
4. Introduce `TaskActivityItem` with the state model above and a deterministic projection. It does no network or SwiftUI work.
5. Add comment operation kinds confirmed by the API spike to the account-scoped `Outbox` with the coalescing, cancellation, dependency, retry, idempotency, and optimistic-identity rules above.
6. Fetch comments when a positive-id task detail opens and render the merged timeline below the subtask card in `InlineTaskEditor`. Preserve loading, empty, partial-page, pending, and failed states.
7. Keep task description, notes rich text, subtask semantics, and the existing completion interaction unchanged.

## Open Questions

- Which exact v2 endpoints and HTTP verbs does the current Vikunja server expose for comment update and delete, and what pagination envelope does comment listing return?
- Which comment fields identify the current author and allowed edit/delete actions? The UI must not offer a destructive control that the server will refuse.
- Is a related subtask list always one level deep in Veyrn's routed task response? The first release should explicitly define whether only immediate children create timeline entries.
- What should the UI show when an optimistic offline comment is edited or deleted before its create operation has reached the server?

## Success Criteria

1. Opening an existing online task shows a single timeline, ordered newest first, containing its server-backed creation event, its existing comments, and completion events for its direct subtasks when `done_at` is nonzero.
2. The timeline never emits an automatic row solely from `updated`; each automatic row names a concrete event.
3. A user can perform every comment operation confirmed by the contract spike when the server permits it. The UI surfaces server permission or validation failures without losing a local draft.
4. Comment create/edit/delete while offline survives app restart, appears with an explicit pending state, and reaches the corresponding server-visible result after sync resumes. A create followed by delete before sync produces no server comment.
5. The existing description editor and subtask completion behavior continue to work unchanged.
6. Unit tests cover projection ordering, zero timestamps, equal timestamps, direct-subtask completion events, optimistic/server ID replacement, all outbox dependency sequences, and every loading/error/empty state.
7. API integration tests run against isolated test accounts/projects/tasks with owned cleanup. They cover every confirmed comment operation, pagination, confirmed authorization failure behavior, and outbox retry behavior against the supported API version.

## Reviewer Concerns

The document completed the three permitted adversarial-review rounds. These implementation gates remain deliberately unresolved until the feasibility spikes run:

1. **Gate acceptance:** record each spike in `docs/designs/activity-contract/` with a request/response fixture, pass/fail checklist, named reviewer, and explicit “unblocks UI work” decision.
2. **Refresh states:** define `acknowledged`, `pending`, `retryableFailed`, `permanentlyFailed`, `cancelled`, and draft states, then state exactly which permit refresh and how a permanent failure is reconciled.
3. **Subtask inclusion:** verify the live relation direction and implement exactly one completion entry for each child returned as `related_tasks.subtask` of the viewed task with a nonzero `done_at`.
4. **Validation assignment:** convert the existing preview into a scoped post-release validation plan or remove the five-day exercise from this implementation design.
5. **Ambiguous create:** treat server create idempotency as an API-spike finding. If Vikunja offers neither an idempotency key nor a searchable correlation field, retain an unresolved pending comment and require explicit user reconciliation rather than promising duplicate-free retry.

## Engineering Review Addendum

Approved in the engineering review:

1. Keep `PendingOp` unchanged. Add a **separate, versioned `CommentOutbox`** that uses `TaskRef` to defer a comment until an offline-created parent task receives its server ID. This avoids the existing whole-queue `try?` decode path silently losing queued task changes after a schema mismatch.
2. Replace the cursor assumption with a `CommentPage` adapter around the server's page-number and `total_pages` envelope. It fetches one page at a time and gives the UI a boolean “load earlier activity” capability without exposing page mechanics.
3. Add a test target and injectable transport before feature code. There is currently no XCTest/Testing infrastructure, so the activity projection and the comment-outbox state machine must establish the test foundation rather than rely on nonexistent test patterns.
4. Keep activity-only types in app/iOS/macOS sources unless they are added to both watch target allowlists. `VikunjaModels.swift` and `VikunjaAPI.swift` compile for watchOS; any symbol they reference must also compile there.

## Design Review Addendum

### What already exists

- `InlineTaskEditor` provides the exact visual vocabulary: 20 pt horizontal inset, 18 pt inset cards, primary/muted text, hairline separators, and the platform blue accent.
- Its subtask card establishes the compact header-plus-row layout Activity should reuse rather than creating dashboard cards.
- Existing native menus and destructive confirmations are the action vocabulary; Activity adds no custom popover or gesture-only action model.

### Not in design scope

- **A global activity stream:** deferred until the per-task projection has proven useful; it must reuse these event and interaction rules.
- **Generic “task updated” entries:** excluded because they do not explain what changed and make the diary noisy.
- **Rich comment attachments, reactions, mentions, and notifications:** excluded because the feature’s job is task continuity, not collaboration chat.
- **Decorative animation:** excluded; motion would not improve the user’s orientation or recovery flow.
